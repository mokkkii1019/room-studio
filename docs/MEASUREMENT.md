# 計測設計メモ（GA4 ＋ クリック計測）

集客（SEO/note/SNS）の効果と、収益（アフィリエイト）に最も近い先行指標を継続的に見るための最小計測設計。
**GA4の注入コードは実装済み**（`GA4_ID` 環境変数を設定すると配信時に gtag.js を注入）。本書は「何を見るか」「どう設定するか」「将来どこを差し替えるか」をまとめる。

> **拡散（SNS投稿）を始める前に読むところ：** §6（UTM命名規約・内部リンクにUTMを付けない理由）／§7（運営自身の除外）／§8（アプリ内ブラウザの制約）／§9（疎通確認手順）／§10（GA4管理画面の未了設定）。指示030の調査と指示031の実装で追記した。

---

## 1. 有効化の手順（ユーザー実施）

1. [Google Analytics](https://analytics.google.com/) で **GA4 プロパティ**を作成し、**ウェブデータストリーム**を追加。
2. 発行される**測定ID**（`G-XXXXXXXXXX`）を控える。
3. Vercel → **Settings → Environment Variables** に `GA4_ID = G-XXXXXXXXXX` を設定（Production／必要なら Preview）→ **再デプロイ**。
4. トップページを開き、GA4 の「リアルタイム」に自分のアクセスが出れば有効化成功。
   - 自分のクリックを除外したい場合は、URL に `?notrack=1` を付けて一度アクセス（`localStorage` に記録され、以後 GA4・`/track` とも送信停止。`?notrack=0` で解除）。**LP・アプリのどちらで付けても効く**（指示031・A1 で修正。それ以前はアプリでしか効かなかった）。
   - **この除外はブラウザのストレージ単位**なので、SNSのアプリ内ブラウザには引き継がれない。拡散期に効いてくる落とし穴なので §7・§8 を必ず読むこと。

> 未設定なら解析オフ（何も送信しない）。ローカル検証時のみ `.env` に `GA4_ID` を置いてもよいが、本番はVercelの環境変数で管理する。

## 2. 見るべき指標（優先順）

| 優先 | 指標 | 取得元 | 意味 |
|---|---|---|---|
| ★★★ | **`select_item`（商品クリック）** | GA4イベント / `/track` | **収益に最も近い先行指標**。アフィリンクのクリック数。 |
| ★★☆ | **収集実行**（家具を集めた回数） | （未計測・下記§4で追加候補） | アプリの中核操作。エンゲージメントの証。 |
| ★★☆ | **アプリ起動 / 画像読み込み** | （未計測・下記§4） | 「触ってみた」到達。LP→アプリの転換の分母。 |
| ★★☆ | **流入（ページ別・チャネル別）** | GA4 標準（page_location / session_source） | どのLP・どのチャネル（note/SNS/検索）が効いているか。 |
| ★☆☆ | 滞在・直帰・スクロール | GA4 標準（拡張計測） | LPのコンテンツ品質の目安。 |

### LP → アプリ の転換を見る仕掛け（実装済み）
- 各LPの CTA は `/?ref=lp-<slug>` へリンク。GA4 は `page_location` にこの `ref` を含むため、**どのLP経由でアプリに来たか**を GA4 上で分別できる（アプリ側の改修は不要）。
- 例：GA4 探索で `page_location` に `ref=lp-hitorigurashi-sofa` を含むセッションを絞り込み、その後の `select_item` 数を見る。

## 3. 実装済みのイベント／エンドポイント

### `select_item`（GA4イベント）＋ `/track`（サーバーログ）
`room-studio.html` の `trackClick(id, type, url, shop)` が、商品の「詳細/購入」クリック時に発火：

- **GA4**: `gtag('event','select_item', { item_id, link_type, link_url, shop })`
- **サーバー**: `GET /track?id&type&url&shop&src=web` → `_site.log_track()` が1行を stdout に出力（Vercelのファンクションログに残る）

パラメータの意味：
- `item_id` … 楽天 itemCode 等の商品ID
- `link_type` … `library:<source>` or `layer:<source>`（クリック箇所×収集元）
- `link_url` … 遷移先（アフィリンク）
- `shop` … **メーカー/店舗名**（STEP0 で追加。メーカー別のクリック分析用）

### メーカー別計測（STEP0 での軽微追加）
- 収集商品は `shop`（店舗名）を保持している。`trackClick` の第4引数に `shop` を渡すよう追加し、`/track` と `select_item` の両方に含めた。
- これにより「どのメーカー/店舗の商品がクリックされたか」を後から集計できる（GA4 のカスタムディメンションに `shop` を登録すれば探索で軸にできる）。
- 過剰実装は避け、既存の2クリック導線（ライブラリ / レイヤー）にのみ適用。

## 5. `/track` の「後で差し替える箇所」（課題#6）

現状 `/track` は**集計DBを持たず stdout ログのみ**。本格的な集計には差し替えが必要。

- 差し替え箇所は **1関数に集約済み**：`api/_site.py` の `log_track(event)`。
  ```python
  def log_track(event):
      # 現状: print("TRACK " + json.dumps(event))  ← Vercelログに出るだけ
      # 将来: ここを DB / KV / 外部計測SaaS への書き込みに差し替える（呼び出し側は無改修）
  ```
- 呼び出し側（`/track` エンドポイント）は `event` dict を渡すだけなので、**`log_track` の中身を変えるだけ**で永続化先を追加できる（例：Vercel KV、Supabase、外部イベントAPI）。
- GA4 で足りる指標は GA4 に寄せ、`/track` は「サーバー側で確実に取りたい生ログ」用途に温存する、という役割分担が現実的。

## 6. キャンペーン計測（UTM）— 調査結果と命名規約

> 指示030 の調査（2026-08-01）と指示031 の実装で確定した内容。**拡散（SNS投稿）を始める前にここを読むこと。**

### 6-1. 結論：UTMはコード変更なしで機能する（本番実測）

| 確認したこと | 結果（2026-08-01・roomstudio.jp 実測） |
|---|---|
| アプリ `/?utm_source=...&ref=lp-...` | 200・UTMも`ref`も素通し。`GA4_ID` 注入済み |
| LP `/lp/<slug>?utm_...` | 200・gtag.js ローダーと `gtag('config',...)` 注入済み |
| `www.` → apex（307）／`http` → `https`（308） | **クエリ保持**。UTMは落ちない |
| 退役スラッグ `/lp/hokuo-interior?utm_...`（301） | 調査時は**クエリ消失** → 指示031・A3 で修正済み |

取りこぼしが起きない根拠：`inject_ga4()` はURLに触れない／アプリに `history.replaceState`・`pushState`・`location.href=` が**1つも無い**（＝非同期で届いた gtag.js が `location` を読む時点でもUTMが残る。ここが最も典型的な取りこぼし要因だが該当なし）／`vercel.json` もCSPメタタグも無いので googletagmanager がブロックされない。

### 6-2. UTM命名規約（確定・指示031-3）

```
https://roomstudio.jp/lp/moyougae-simulation
  ?utm_source=x                 # x / instagram / pinterest / note / tiktok
  &utm_medium=social            # ★全媒体で必ず social に統一
  &utm_campaign=x-20260801-a    # ★投稿単位の識別子。<媒体>-<日付YYYYMMDD>-<連番>
  &utm_content=hero-a           # 任意。A/B や配置位置の区別のみ
```

- **`utm_medium` は必ず `social`。** 媒体名（`x`・`instagram` 等）を入れると GA4 の既定チャネルグループから外れて **Unassigned** に落ち、チャネル別の集計ができなくなる。媒体は `utm_source` が持つ。
- **投稿単位の識別子は `utm_campaign` に入れる。** 「セッションのキャンペーン」は GA4 の標準レポートでも探索でも使える一級ディメンションだから。`utm_content`（手動広告コンテンツ）は参照できる場所が限られる。施策単位でまとめたいときは `x-202608` のような**前方一致**で絞る。
- **`utm_campaign` に着地先（LP / アプリ）を混ぜない。** 着地先は `page_location` の `/lp/` の有無で判別できる。混ぜると「同じ投稿の効果」が着地先ごとに分裂して比較できなくなる。
- **`utm_content` は任意。** 同一投稿内でリンクを複数置く場合の区別だけに使う。

### 6-3. ★ LP→アプリの内部リンクにUTMを付けてはいけない

LPのCTAは `/?ref=lp-<slug>`（`api/_site.py` の `app_url`）で、**UTMを付けていない。これは意図的で、絶対に変えないこと。**

- **同一ドメインの内部遷移にUTMを付けると、GA4はそこでセッションを切り直してキャンペーンを上書きする。** SNS由来（`utm_campaign=x-20260801-a`）で来た人が、LPのCTAを押した瞬間に「LP由来」に化ける。流入元が丸ごと失われる、最も痛い壊し方。
- 現状は壊れていない：LPで受けたUTMは**セッション単位で保持される**ため、CTA先のアプリのURLにUTMが無くてもアトリビューションは維持される。アプリ側の `page_view` は `session_source/medium/campaign` を継承する。
- 「どのLP経由でアプリに来たか」は `ref=lp-<slug>` が `page_location` に残るので、そちらで分別する。**`ref` は GA4 がキャンペーンとして解釈しないパラメータなので、UTMと併存しても干渉しない**（実測確認済み）。

> 一行でいうと：**外部からの流入は `utm_*`、サイト内の導線は `ref=`。この境界を越えないこと。**

## 7. 運営自身の除外（`?notrack`）と内部トラフィック

### 7-1. 現在の方式（既定）

`?notrack=1` → `localStorage.rs_notrack='1'` → **gtag.js を一切読み込まない／`/track` も送らない**。`?notrack=0` で解除。
アプリ（`room-studio.html` の `const GA4_ID` ブロック）とLP（`_site.ga4_head_snippet()`）の両方が、このフラグを**読みも書きもする**（指示031・A1）。

> **A1で直したこと：** 以前はLP側がフラグを**読むだけ**だったため、`/lp/<slug>?notrack=1` を最初に叩いても除外されず、そのアクセスが記録されていた。「先にアプリを踏んでいれば効く」という順序依存で、頼りたいときに限って失敗する形だった。同一オリジンなのでフラグ1つで両方カバーされる。

### 7-2. この方式の弱点

**除外が効いている端末では、UTMのテストができない。** 何も送信されないので、リアルタイムにもDebugViewにも一切出ない。確認するには除外を一時解除するしかなく、戻し忘れれば本番データが汚れる。

### 7-3. `GA4_INTERNAL_TRAFFIC=1`（A2）— 除外を維持したままテストする

環境変数 `GA4_INTERNAL_TRAFFIC=1` を入れると、除外端末でも **GA4にだけ** 送るようになる：

```js
gtag('config', GA4_ID, {traffic_type:'internal', debug_mode:true})
```

除外は GA4 側の「内部トラフィック」データフィルタが行う。`/track`（サーバーログ）はフィルタの仕組みを持たないので、**除外端末からは従来どおり一切送らない**。この非対称は意図的。

#### ★★ 有効化の順序（ここを間違えると除外が完全に無効になる）★★

**GA4管理画面の設定が先、環境変数が後。** 片方だけでは意味を持たない。

1. GA4 → 管理 → データストリーム → タグ設定 → **内部トラフィックの定義** で運営のIPを登録（`traffic_type` の値は既定の `internal` のまま）
2. GA4 → 管理 → **データフィルタ** で内部トラフィックのフィルタを作成
3. フィルタが存在することを確認したうえで、Vercel の環境変数に `GA4_INTERNAL_TRAFFIC=1` を追加 → 再デプロイ
4. 除外端末でアクセスし、意図どおり除外されていることを確認

> **フィルタを作らずに 3 だけやると、運営の自己クリックがそのままレポートに入る＝除外が完全に無効になる。** 環境変数を未設定（既定）のままにしておけば、従来どおり「何も送らない」ので安全側に倒れる。

#### 確認のしかた（フィルタ有効時）

- データフィルタの状態を一時的に **「テスト」** にすると、データは除外されず「テストデータのフィルタ名」ディメンションで識別できる状態で計測される。**UTMがキャンペーンとして認識されるかを確実に確認できるのはこの状態。** 確認後に「有効」へ戻す。
- `debug_mode:true` を付けているので DebugView にも流れるが、**フィルタが「有効」のとき DebugView に出るかは未確認**。まず DebugView を見て、出なければ上の「テスト」状態を使う。

## 8. アプリ内ブラウザ（X・Instagram）の制約

拡散の主戦場はSNSのアプリ内ブラウザ（iOS: WKWebView / Android: Custom Tabs）。**ここは見落とされやすいので、投稿前に必ず確認すること。**

| 観点 | 実態 | 影響 |
|---|---|---|
| GA4が動くか | **動く**。JS・first-party cookie とも利用可。CSPも無いので固有のブロック要因は無い | — |
| UTMの解釈 | **問題なし**。URLのクエリを読むだけなのでブラウザ環境に依存しない | — |
| `document.referrer` | **空になりやすい**（SNSはリファラを落とす設定が一般的） | **UTMなしだと `(direct)/(none)` に落ちる。** チャネル別すら分からない → **UTMは「あると良い」ではなく必須** |
| ストレージ | **アプリごとに分離**。Xアプリ内 ≠ Instagramアプリ内 ≠ Safari | 同一人物が別ユーザーとして数えられ、**ユーザー数・新規率が実態より多く出る**（キャンペーン帰属自体は正しい） |
| `_ga` cookie の寿命 | Safari / WKWebView の ITP により JS発行cookie は **7日で失効** | 8日後の再訪は新規ユーザー扱い。**着地セッションの帰属には影響しない** |
| **`?notrack` 除外** | **効かない**（ストレージが別） | **運営が自分の投稿をXアプリから開いて確認したクリックは全部カウントされる。** 拡散初期は母数が小さいので無視できない汚染になる |
| `/track` の送信 | `fetch(..., {keepalive:true})` ＋ gtag の sendBeacon なので、`target="_blank"` の離脱でも残る想定 | アプリ内ブラウザは新規タブを開けず同一WebViewで遷移する実装があるため、**実機確認が望ましい**（`docs/OPEN_ITEMS.md` A1） |

> **計測とは別のリスク：** アプリ内ブラウザはWKWebViewでメモリ制約が厳しく、331KBのHTML＋canvas処理を行うこのアプリはタブ落ち→リロードが起きうる位置にいる。起きると `page_view` が水増しされ、直帰率も歪む。→ `docs/OPEN_ITEMS.md` A1 に実機確認項目として追加済み。

## 9. 拡散前の疎通確認手順（運営・5分）

ローカルのスタブでは見つからない不具合があるので、**本番で実際に押して確かめること**。

1. スマホのSafari（除外していない状態）で
   `https://roomstudio.jp/lp/moyougae-simulation?utm_source=x&utm_medium=social&utm_campaign=probe-0801`
2. GA4 **リアルタイム** →「セッションのキャンペーン」に `probe-0801` が出るか
3. そのままCTAでアプリへ → **同じセッションのままキャンペーンが `probe-0801` を維持**しているか
   （§6-3 の「`ref` とUTMの併存」の実地確認。ここが崩れていたらCTAのURLを疑う）
4. 商品の「詳細」を押す → リアルタイムのイベントに **`select_item`** が出るか、かつキャンペーンが維持されているか
5. **★ Xに非公開の投稿を1つ作り、Xアプリ内ブラウザから同じUTM URLを開く** → リアルタイムに出るか（§8 の最重要確認）
6. 終わったら `https://roomstudio.jp/?notrack=1` で自分を除外
   （A1適用後はLPの `/lp/...?notrack=1` でも効く。ただし**アプリ内ブラウザには引き継がれない**）
