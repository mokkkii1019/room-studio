## 1. 設計判断: 既存 `scoreCandidate` の拡張ではなく、**別のスコア**にした

引き継ぎで「既存の候補スコアラーの拡張なのか別物なのか、設計判断して報告」と言われた点。

**別物にした。** 理由は3つあり、いずれも実測に基づく。

### (a) 目的が違う。既存スコアは「除外」に使われている
`scoreCandidate`（改め `candSelScore`）は **選別**用で、①商品ごとの候補3枚から1枚を選ぶ
②3倍取得した中から上位K件だけ配る、の両方を決めている。指示016 は「**除外はしない**」と
明言しているので、この判定を触ると要件から外れる。新しい `candPlaceScore` は
**配られた結果の並び順にしか使わない**。判定を外しても配られる中身は1枚も変わらない。

### (b) 「無地背景を評価する」項は、選別に入れると必ず壊れる
`docs/COLLECT_QUALITY_RESUME.md` に記録がある旧スコアラーの失敗そのもの
（縁が無地で明るいものを加点 → カラーバリエーション表が最高得点になる）。
今回もこれを実測で再現した。**候補の選び直しを実装して測ったら逆効果だった**:

| 同一商品(`sofa` 072)の候補 | 中身 | 選別スコア | 配置しやすさ |
|---|---|---|---|
| `072_0.jpg` | 実写（部屋の中のソファベッド） | -1.17 | **-5.51** |
| `072_2.jpg` | 「REVIEW RATING 4.21 ★★★★ レビュー数：124件」の**カード** | -1.76 | **-3.80** |

配置しやすさで候補を選ぶと、**レビュー点数カードが実写に勝つ**。同様に寸法図
(`019_2` -4.64) やイラストのブランドカード (`000_1` -4.71) も浮く。いずれも
「無地の背景に被写体ひとつ・画枠に接していない」という特徴を完全に満たしてしまう。

→ **候補の選び直しには使わない。** コードにもそう書いた（`pickBestCandidateThumb`）。
並び順にだけ使うぶんには、除外が起きないので同じ罠に落ちない。

### (c) 「良い」の定義が違う
既存の評価セット（`dev`/`holdout`/`delivered`）では **`ok` = 部屋の中の写真でも被写体が
明確なら採用可**としていた。指示016 は逆に**部屋の中に置かれた状態を「深刻」**と名指し
している。同じ評価セットでは測れないので、新しいラベル体系で測り直した（下記）。

## 2. 実装した指標

すべて `candPixels` が作る**同じ 256×256 バッファ**から計算する（画像の再取得なし）。

| 指標 | 何を見ているか | AUC（配置しやすい画像 vs それ以外・210枚） |
|---|---|---|
| **ringPure** | 外周8%の帯が、**帯自身の代表色**と一致する画素の割合 | **0.913** |
| **fgBorder** | 画枠2pxのうち、背景色と違う画素の割合 | **0.891** |
| **ringEdge** | 外周帯のエッジ密度 | **0.838** |
| textPx / glyphs | 文字（既存 `candTextScore` を再利用） | 0.899 / 0.875 |
| （参考）既存の選別スコア | | 0.853 |

- `ringPure` が高い＝背景紙の上に置いた撮影。低い＝部屋の中／合成物。
- `fgBorder` が高い＝被写体が画枠で切れている、または背景がそもそも分離できない（部屋）。
- 代表色は**ヒストグラム中央値**で取る。`np.median` は偶数個で2値の平均を返すため、
  ブラウザ実装と一致しない。エッジもRGBの**和**の整数で測り2乗のまま比較する
  （float32 に落とすと1ULPずれ、閾値ちょうどの画素で数が変わって照合が落ちた。実際に落ちた）。

### スコア式

```
place = sel
      - 1.2 * clamp01((0.75 - ringPure) / 0.45)     背景の単純さ
      - 0.3 * clamp01((fgBorder - 0.10) / 0.35)     見切れ・部屋の中
      - 0.6 * clamp01(ringEdge / 0.10)              背景のざわつき
      - 0.3 * clamp01(glyphs / 45)                  文字（個数）
      - 2.0 * clamp01(textPx / 0.09)                文字（面積）
```

減点のみ。土台の `sel` に合成物の継ぎ目・仕切り・彩度の項が入っているので、それはそのまま
効く。重みは 210枚のラベルに対する**多点スタート座標探索**＋**カテゴリ1つ抜き検証**で決め、
最後は各分割の中央値に近い丸い値に手で寄せた（分割ごとに最適重みがかなり動くため、
探索結果をそのまま採ると過学習する）。

### 採用しなかった指標と、その理由（すべて実測）

| 指標 | 判定 | 実測 |
|---|---|---|
| **縦横比** | ❌ **不採用** | 全845候補の縦横比は **0.56〜1.81** に収まり、極端なものが1枚も無い。減点対象がゼロなので入れる意味がない。AUC 0.568 |
| **被写体の個数（連結成分の数）** | ❌ **不採用** | **AUC 0.587＝ほぼ無情報。** 合成物はパネル同士が接して1塊に融合し、逆にソファ＋オットマンのような正当な商品が2塊に割れる。指示に明記された項目だが、この作り方では機能しない |
| **前景の占有率** | ❌ **不採用** | 単体では AUC 0.876 と悪くないが、`ringPure`/`fgBorder` と同じ背景差分から作られるので**完全に冗長**。重み探索でも全7分割で 0 になり、入れると `meanRank` がむしろ悪化した |
| ringStd（外周の標準偏差） | ❌ 置換 | 商品の脚が帯に1本掛かるだけで跳ねる。`ringPure` に置き換え（前者は clean 画像で 46〜67、後者は 0.9 前後で安定） |
| 四隅の明度のばらつき | ❌ 置換 | 同上。`ringPure` に吸収 |
| 前景ブロブの縦横比・充填率（接写よけ） | ❌ 不採用 | 接写と clean が分離しない（充填率 中央値 0.69 vs 0.33 だが四分位が重なる） |
| **候補画像の選び直し** | ❌ **不採用** | 上記 1-(b)。逆効果 |

## 3. クライアント判定にした理由

**クライアント側。** サーバー側は検討して外した。

- 判定に使う画像は**すでにクライアントが読んでいる**（3倍取得→上位K件の選別で、全候補を
  300pxで読み込んで採点している）。サーバーで判定するなら**サーバーが同じ画像を取り直す**
  必要があり、楽天CDNへのリクエストが倍増する。
- **スコアをサーバーに蓄積しない**という要件（指示2項）にそのまま合う。サーバーは
  何も覚えないし、判定コードすら持たない。
- Vercel の関数は**標準ライブラリのみ**（`api/_collect_core.py` の冒頭に明記）。
  画像処理を入れると numpy/Pillow が要り、バンドル方針が崩れる。

### 体感速度への影響（実測）

採点コードそのものを `room-studio.html` から取り出して実バッファで計測
（`node bench.js`、24枚×30回）:

| | 1枚あたり |
|---|---|
| 現行（選別スコアのみ） | 8.16 ms |
| **新（選別＋配置しやすさ）** | **8.56 ms（+0.40 ms / +5%）** |
| 参考: 文字検出を共有しない実装 | 14.43 ms（+77%） |

文字検出（連結成分のラベリング）は選別スコアと共有している。共有しないと +77% になるので、
**この共有は必須**（`candScores` が `candTextScore` を1回だけ呼び、両方に渡す）。

収集1回の実測（本番 `roomstudio.jp` に対して、ブラウザと同じ並列数で計測）:

| 段階 | sofa | floor_lamp |
|---|---|---|
| `/collect` | 9.07 s | 6.64 s |
| 判定用サムネ（219/266枚・並列6） | 22.28 s | 23.27 s |
| 原寸30枚（並列5） | 4.93 s | 5.00 s |
| **合計** | **36.28 s** | **34.91 s** |

追加される計算は 0.40 ms × 約220枚 ≒ **88 ms（並列6なので実時間では約15 ms）**。
**収集全体の 0.3% 未満**で、体感できる差ではない。ネットワークが支配的な処理である。

### 4-3. カテゴリによる効きの違い（重要）

- **効く: sofa / dining_table / floor_lamp / plant。**
  無地背景の商品写真が実在するカテゴリでは、それが確実に先頭1〜2枚に来る。
  sofa は「先頭2枚が部屋の写真」から「先頭2枚が無地背景の単体写真」に変わる。
  floor_lamp は部屋の写真が上位10件から**3枚→0枚**に消え、無地背景が3→5枚に増える。

- **効かない: carpet。** これは並び替えの問題ではなく **在庫の問題**。
  ラグは「白背景に敷物だけ」という写真が楽天にほぼ存在せず、30枚中の内訳は
  文字17・合成物5・人物5・部屋3で、**配置しやすい画像が0枚**だった。
  素足・スリッパ・「25mm厚」「低反発」の見出しが定番の売り方になっている。
  **並べ替えても順番が入れ替わるだけで、見た目はほとんど変わらない**（比較シート参照）。

- **効きが限定的: shelf。** 上位30件のうち7枚が**同一店舗のほぼ同じバナー**
  （「No.1 SteelRack Luminous」＋ワイヤー棚の接写）で埋まっており、これが3枚ぶん下がる
  代わりに寸法図が上がる。**重複対策（同一店舗の連続を割る）が別途必要**（§6）。

- **chest** は元から部屋の写真が中心で、上位10件から文字・合成物が消えて（1→0, 1→0）
  部屋の写真に置き換わった。指示の基準では部屋の写真も深刻なので、
  **改善とも言い切れない**（正直に書く）。

### 4-4. 失敗例（指示4項）

#### ❌ スコアは最高なのに実際は使えない — 接写
`floor_lamp` の**新順位1位**がこれ。

- `https://thumbnail.image.rakuten.co.jp/@0_mall/auc-rmjapan/cabinet/item_image/lighting/floorlamp/arco5.jpg?_ex=600x600`
- Arco Lamp（アルコランプ）の**アームの付け根だけを写した接写**
- `ringPure=0.92 / ringEdge=0.017 / fgBorder=0.08 / 文字0` — **全指標が満点級**。
  実際「無地背景に被写体ひとつ、画枠に接していない」を完全に満たしている。
  違うのは「その被写体が商品全体ではない」という一点だけで、それは今の特徴量では見えない。
- `chest` の新順位5位（`tomarigi/…/av-sb-sub1.jpg`＝天板の角の接写）も同型。

**これは `docs/COLLECT_QUALITY_RESUME.md` が「いまの最大の失敗要因」として挙げ、
4種類の対策がすべて失敗したまま残っている問題そのもの**で、今回も解けていない。
今回さらに「前景ブロブの縦横比・充填率」を試したが分離しなかった（§2の表）。
物体検出なしで解けるかは依然として未検証。

#### ❌ スコアは低いのに実は良い — 画枠いっぱいの横長商品
`shelf` の**新順位17位**（現行21位）。

- `https://thumbnail.image.rakuten.co.jp/@0_mall/your-sales-shop/cabinet/0033/2b4rl83st4_0.jpg?_ex=600x600`
- 白背景に木製オープンシェルフ。右上に「楽天ランキング1位」バッジが1つあるだけで、
  **配置素材としては上位に来てよい画像**
- `ringEdge=0.245`（帯の1/4がエッジ）/ `fgBorder=0.33` / `glyphs=23`
- 原因は**商品が横に広くて外周帯を突き抜けている**こと。棚板と支柱が帯を何度も横切るので
  「背景がざわついている」と誤読される。バッジの文字も効いている。
- → **背景の判定は、被写体が小さい商品（照明・小物）に有利で、フレームいっぱいの商品
  （棚・ラグ・ダイニングテーブル）に不利**という系統的な偏りがある。

#### ❌ 上位10件の「深刻」が2枚増えた
70枚中 29→31。無地背景を評価するぶん、**白背景の販促グラフィック**（寸法図・
カラーチップ付きの商品カット）が部屋の写真より上に来ることがある。
指示の基準では文字も部屋も同じく深刻なので入れ替わりに近いが、**画面の見た目としては
「文字が増えた」ように見えうる**。比較シートの `dining_table` と `plant` で確認できる。

## 5. 計測（指示3項）

既存の `/track` と GA4 の仕組みにそのまま乗せた。**個人情報は扱わず、スコアもサーバーに
保存しない**（`_site.log_track` は1行 print するだけで、DBは無い）。

| イベント | いつ | 中身 |
|---|---|---|
| `collect_done` | 収集完了 | `item_category`, `count`, `ranked`(並び替えの有無) |
| `collect_shop` | 収集完了・**店舗ごとに1件** | `item_category`, `shop`, `count` ← **配置率の分母** |
| `place_item` | 部屋に配置した瞬間（同じ品は1回だけ） | `item_id`, `item_category`, `shop`, `source`, `rank`, `score` ← **分子** |

`collect_shop ÷ place_item` を店舗単位で見れば「**どのメーカーの画像が実際に使われ、
どのメーカーの画像は配られたのに使われなかったか**」が出る。これが指示の狙いである
メーカー交渉の材料になる。`rank`（配られた並び順）も入れてあるので、
「上位に置いたものが本当に使われているのか」という並び替えの効果検証にも使える。

- 既存の `select_item`（詳細リンクのクリック）と `trackClick` は**変更していない**。

止めるなら 1 はコード修正、2 は `COLLECT_SHOP_MAX=0`。

## 9. 本番のスコア分布を確認する手順（運営向け・指示018 の5項）

`log` 運用の目的はこれ。**5分で終わる。Vercel も開発環境も要らない。**

### やること

1. Chrome（または Edge）で **https://roomstudio.jp** を開く
2. **F12** を押して開発者ツールを開き、上のタブで **Console** を選ぶ
3. 画面左の「家具」→「画像を収集」で、**種類を選んで収集ボタンを押す**（枚数は既定の30でよい）
4. 収集が終わると Console に次の1行と、続いて**表**が出る

```
[collect-ranking] sofa n=30 mode=log place best=-0.95 med=-5.18 worst=-5.96
```

（数値は 2026-07-30 に本番が配った30枚を採点したときの実測値。同じ桁の値が出る）

5. 表の列は `順 / 選別 / 配置しやすさ / 店舗 / 商品 / url`。
   **`url` 列をクリックすると実画像が別タブで開く**ので、スコアと見た目の対応を確認できる。
6. **カテゴリを変えて数回繰り返す**。少なくとも `sofa`・`shelf`・`carpet` の3つは見ること
   （効く／重複が多い／効かない、の3典型）。

### 何を見て、どう判断するか

見るのは2つだけ。**B は機械的に読めるので先に B、迷ったら A で目で確かめる**。

| 見るもの | `on` にしてよい | `log` のまま様子見 |
|---|---|---|
| **B. 1行目の `best=` の値** | **−1.5 より高い**（例 `best=-0.95`） | −1.5 より低い（例 `best=-1.58`） |
| **A. 上位3件の見た目**（`配置しやすさ` 列の見出しをクリックして並べ替え、上3つの `url` を開く） | 無地背景の商品写真が**2枚以上** | 接写・寸法図・文字入りが**2枚以上** |

**B の −1.5 という数字の根拠**（210枚の実測）: 目視で「配置しやすい」と判定した14枚のうち
**11枚が −1.5 以上**、それ以外の196枚では **7枚だけ**が −1.5 以上。つまり
**`best` が −1.5 を超えていれば、そのカテゴリには配置しやすい画像が実在する**とほぼ言える。
2026-07-30 の実測では7カテゴリ中6つが −1.5 以上で、下回ったのは `carpet`（−1.58）**だけ**
＝配置しやすい画像が0枚だった唯一のカテゴリと一致した。

| 参考: 2026-07-30 の実測 | best | med | worst |
|---|---|---|---|
| floor_lamp | **−0.10** | −2.13 | −3.57 |
| chest | **−0.42** | −3.39 | −4.78 |
| plant | **−0.45** | −4.27 | −6.06 |
| shelf | **−0.66** | −3.10 | −5.72 |
| sofa | **−0.95** | −5.18 | −5.96 |
| dining_table | **−1.09** | −5.29 | −6.39 |
| **carpet** | **−1.58** ← 唯一の不合格 | −5.51 | −6.18 |

- 表は**すでに配置しやすさスコアを持っている**ので、`配置しやすさ` の列見出しをクリック
  すればその場で並べ替えられる（`console.table` の機能）。**これが `on` にした後の
  実際の並び順**になる。押して上位を見れば、有効化後の画面が事前にそのまま分かる。
- **判断はカテゴリ単位ではできない**（フラグは全カテゴリ共通）。3〜5カテゴリ見て
  「多数で合格するか」で決める。`carpet` は原理的に合格しないので除外して数えてよい（§10）。
- A が満たせないカテゴリが多いなら **`on` にしない**。指示018 の重み調整版
  （別ブランチ）を先に検討すること。
- ついでに見ておくとよいもの: **`店舗` 列に同じ店が上位10件で4件以上**あれば、
  多様性確保（指示018 の3項・別ブランチ）を先に入れたほうが効果が大きい。
  2026-07-30 の実測では `carpet` と `shelf` が4件、`chest`・`plant` が3件だった。

### 有効化するとき

`room-studio.html` の `const COLLECT_RANKING='log'` を `'on'` にして main に push。
戻すときは `'log'` に戻して push（どちらも数分でデプロイされる）。

## 11. 同一店舗の重複抑制（指示018 の3項 → 指示019 で本番へ）

### 何が問題だったか
本番が配る shelf の30枚のうち、**上位10件の7枚が同一店舗のほぼ同じバナー**だった
（「ルミナス スチールラック」のレール接写の色・サイズ違い）。1画面が1店舗の同じ絵で
埋まると、ユーザーの選択肢が実質的に無くなる。

### 実装
`diversifyByShop(rows, COLLECT_SHOP_MAX)`（`room-studio.html`）と、同じ動きの
`diversify_by_shop()`（`tools/collect-audit/imgscore.py`）。1店舗が `per` 件を超えたら
超えた分を次の巡へ回す。同じ巡の中の順序は元のスコア順のまま（安定）。

**除外はしない。順番を送るだけ**なので、配られる30枚の中身は1枚も変わらない
（指示016 の「除外はしない」と矛盾しない）。**止めるときは `COLLECT_SHOP_MAX=0`。**

### `per=2` にした根拠（210枚・本番と同じ選別スコア順での実測）

| per | 配置@3 | 深刻@3 | 配置@10 | 深刻@10 | 文字@10 | 同一店舗の最大数 |
|---|---|---|---|---|---|---|
| 0（抑制なし） | 5 | 6 | 11 | 29 | 20 | 2,2,2,3,**7**,3,2 |
| 1件まで | 5 | 6 | **9** | **30** | 19 | すべて 1 |
| **2件まで（採用）** | 5 | 6 | 11 | 29 | **19** | **すべて 2** |
| 3件まで | 5 | 6 | 11 | 29 | 19 | 2,2,2,3,3,3,2 |

指示018 の本文は「**2件目以降**を下位に送る」だったが、`per=1` は実測で逆効果だった
（店舗を割るためにスコアの低い画像を上へ引き上げてしまい、配置@10 が 11→9、深刻が
29→30）。**3件目以降を送る `per=2`** が、品質指標を1つも落とさない最も強い設定。
指示019 でこの修正を承認済み。

### ⚠️ この変更は「上位3枚の指標」では測れない
上表のとおり **配置@3・深刻@3 は動かない**。効くのは3〜9番目で、shelf の同じレール接写7枚が
2枚になり、空いた5枠が別商品5点（2WAY RACK、アイアン×木の棚、白い棚の実写など）に
入れ替わる。**ラベル指標ではなく「同一店舗の最大数」と目視で判断した。**

多様性の変更を評価するときの基準（§12 の補足）:
**「配置@3・深刻@3 を悪化させない」かつ「同一店舗の最大数が下がる」**の2つで見る。

### この変更は `COLLECT_RANKING='log'` でも効く
抑制は並び替えの有無と無関係に「配られた30枚の並び」に効く。したがって
**「`log` だから本番の見た目は変わらない」は成立しない。** 本番の並びは変わり、
品質指標は現行と同じまま重複だけが消える。これを承知のうえで指示019 でマージした。

## 12. 指示018 の重み調整は**不採用** — 判断は「上位3枚」で行う（指示019）

### 何が起きたか
指示018 で「文字の重みを上げ、背景を下げる」調整を行い、
`pure 1.2→0.8 / edge 0.6→0.2 / glyph 0.3→0.6 / tpx 2.0→4.0（飽和 0.09→0.07）`
で **70枚の @10 合計は改善した**（深刻 31→27、文字 21→17）。

**それでも不採用にした。** 比較シートを7カテゴリぶんレンダリングして目視した結果、
**ユーザーが最初に見る上位3枚では悪化していた**:

| カテゴリ | 目視の結果 |
|---|---|
| sofa | **悪化**。1位に YAMAZEN のロゴ・小窓付きバナーが入り、きれいな単体写真が2位→4位へ |
| plant | **悪化**。良いサンスベリアが2位→3位 |
| chest | **悪化**。木口の接写が3位へ |
| shelf | 改善。良い画像が16位→7位 |
| dining_table / carpet / floor_lamp | ほぼ同等 |

@10 の合計が改善したのは主に**4〜10番目の入れ替え**によるもので、ユーザーの体験には
ほとんど寄与しない。

### 決定（指示019）
1. **016 の重みを維持する。** 調整版は `feature/collect-ranking-tuning` に残置（マージしない）。
   重みは `room-studio.html` の `candPlaceScore` と `tools/collect-audit/imgscore.py` の
   `place_score` の2か所にあり、`--parity` が**スコアそのものを突き合わせる**ので
   片方だけ直すと必ず落ちる。
2. 🔴 **今後、並び替えの評価は「深刻@10」ではなく「上位3枚」を基準とする。**
   ユーザーが見るのは上位3枚であって10枚の合計ではない。`'on'` への切り替えを検討する
   ときも、この基準で測り直すこと。`eval_place.py` の表は **@3 を左に置いてある**。
3. **深刻@10 という指標自体が、位置を区別しないぶん粗すぎた**というのが今回の最大の学び。
   数値が動いても体感が変わらない（`docs/TRY_MASK_INVESTIGATION.md` の失敗）を、
   指標設計の側で繰り返していた。

### 比較シートの再生成と、目で見る手順

```sh
# 1) 数値と比較シート（画像は毎回 <cache> に取得。楽天規約によりリポジトリには入れない）
python tools/collect-audit/eval_place.py <cache-dir> --sheet docs/collect-ranking-compare.html

# 2) ブラウザで開くだけなら docs/collect-ranking-compare.html をそのまま開く
```

ブラウザを開かずに（またはエージェントが自分で）目視したい場合は、カテゴリごとに切って
headless Chrome で撮る。**撮った PNG は見たら消すこと**（楽天画像を残さない）:

```sh
# <sheet> をカテゴリ単位に分割 → 1カテゴリずつ 1520x1120 で撮る
chrome --headless=new --disable-gpu --hide-scrollbars \
       --virtual-time-budget=20000 --window-size=1520,1120 \
       --screenshot=shot.png "file:///…/cmp-<category>.html"
```

分割は `<h2>` 単位で切って先頭の `<style>` を付け直すだけでよい。`loading="lazy"` を
外しておかないと画面外の画像が読まれない。
