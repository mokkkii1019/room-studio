# `/try`・`/demo` 所見と再設計の見込み（2026-07-30）

運営判断で両ページを非公開にしたのを受け、**再設計の判断材料**として実物を触って確認した
所見をまとめる。非公開化の手順とフラグは `docs/BUZZ_FOUNDATION_REPORT.md` の冒頭を参照。

確認方法: 本番URLを iPhone 17 相当（390×844・DPR3・タッチ有効）で開き、壁6色・床5色の
全スウォッチ、家具トグル、見比べトグルを実際に操作。`/demo` は 9:16・clean で実時間
15秒ぶんを 2.5秒間隔でコマ取りした。

---

## 1. `/try` の魅力を損ねている要因

家具のシルエット以外にも複数ある。**影響の大きい順**に並べる。

### 1-1. 🔴 バグ: 色を変えた直後に「BEFORE」と表示される

**初回に色を変えた瞬間、AFTER の状態なのにバッジが「BEFORE」と出て、そのまま残る。**

原因はスウォッチのクリックハンドラ（`api/_site.py` の `try_html` 内）:

```js
bd.classList.toggle('on', !!(RS.state.wall||RS.state.floor));   // 表示にするだけ
```

バッジの**文言を更新しているのは `setBefore()` だけ**で、こちらは呼ばれない。初期HTMLが
`<span class="badge">BEFORE</span>` なので、最初の1回は必ず「BEFORE」が出る。「変わった」
と伝えるべき瞬間に「変わる前」と書いてあることになり、体験の中心を正面から壊している。

実測した状態遷移（`aria-pressed` とバッジ文言）:

| 操作 | 見比べトグル | バッジ |
|---|---|---|
| 初期 | false | （非表示） |
| 壁スウォッチをタップ | false | **「BEFORE」が表示される** ← 誤り |
| 家具ON | false | 「BEFORE」のまま |
| 見比べON | true | 「BEFORE」（ここでは正しい） |
| 見比べOFF | false | 「AFTER」＋**表示されたまま残る** |

### 1-2. 🔴 選べる色がほぼ全部「ほぼ白」で、変化が見えない

壁6色のうち「生成り／グレージュ／淡いグリーン／ブルーグレー」は**いずれも明度の高い
淡色**で、白い壁から切り替えても差がほとんど分からない。はっきり変わるのは「チャコール」
だけ。**タップしても何も起きていないように見える**確率が高く、「変えられる」という体験の
一番おいしい部分が伝わらない。

床は「ウォルナット」など振れ幅があり、こちらは変化が分かる。**床のほうが体験として成立
している**。

### 1-3. 🟠 部屋が空室で、そもそも憧れが無い

サンプル部屋は**家具も生活感も無い賃貸の空室**で、窓の外は白飛びしている。模様替えは
「素敵にしたい」動機で来るのに、出発点が事務的な空室なので、色を変えても「片付いた空室」に
しかならない。SNS から来た人が最初に見る絵として弱い。

### 1-4. 🟠 家具が半透明のシルエット（素材未配置）

`lp-assets/try-furni-1` が**本番で404**のため、プレースホルダのソファが出る。半透明で床が
透け、影も接地感も無く、**画像の読み込み失敗に見える**。これは素材を置けば直る。

### 1-5. 🟡 壁の色が「塗った」ではなく「フィルタを掛けた」に見える

元写真の陰影がある程度は残るものの、面ごとに一様な色が乗るため平板になる。とくに淡色では
「壁紙を変えた」というより「画面に色被りが出た」ように見える。天井を対象外にしている
（窓を避けるための設計）ので、壁と天井の境界が硬い線で出るのも人工的に見える一因。

### 1-6. 🟡 スウォッチが右端で見切れている

壁の色の行は横スクロールだが、最後の「チャコール」がラベルごと画面端で切れている。
スクロールできると気づかず、**一番変化が分かる色に到達しないまま離脱**しうる。

### 1-7. 🟡 主役の絵が小さい

3:2 のステージがページ上部に置かれ、390×844 の画面では**縦の3割程度**しか占めない。
残りはスウォッチ・ボタン・CTA・注釈で、「部屋を見て楽しむ」より「フォームを操作する」
画面に見える。

## 2. `/demo` が拡散素材に耐えない要因

`/try` と同じ描画エンジン・同じ素材なので、上の 1-2〜1-5 をそのまま引き継いでいる。
動画固有の問題は次のとおり。

- **変化が見えない**。15秒の1周のうち、はっきり色が変わって見えるのは2回だけ。実時間で
  コマ取りすると、6コマ中4コマがほぼ同じ「オフホワイトの空室」に見える
- **止め絵に近い**。カメラも寄りも無く、色のクロスフェードだけ。SNS はスクロールを止める
  最初の1〜2秒が勝負だが、その1〜2秒に起きるのが「淡い色がゆっくり変わる」だけ
- **9:16 のトリミングが窮屈**。横位置の部屋写真を縦に切るため窓が画面の大半を占め、
  部屋の広がりが伝わらない。白飛びした窓が中央にあり、視線が外に逃げる
- **ソファのシルエットが最も目を引く**。動画で唯一の「物体」が半透明の灰色の塊なので、
  完成度が低く見える最大の原因になっている

## 3. 設計そのものの限界か、素材が揃えば十分か

**素材だけでは足りない。** 内訳は次のとおり。

| 要因 | 素材で直る | 実装で直る | 設計の作り直しが要る |
|---|---|---|---|
| 1-1 BEFORE バッジのバグ | | ✅ 数行 | |
| 1-6 スウォッチ見切れ | | ✅ 小 | |
| 1-4 家具のシルエット | ✅ PNG 1枚 | | |
| 1-2 色の振れ幅が無い | | ✅ 色の選び直し | |
| 1-5 塗りがフィルタに見える | | △ 陰影の乗せ方を改善 | |
| 1-3 空室で憧れが無い | △ 写真を替える | | ✅ |
| 1-7 絵が小さい | | ✅ レイアウト | |
| 2 動画に山が無い | | | ✅ |

つまり **1-1・1-4・1-6 は明確に「直せる不具合／欠品」**、1-2・1-7 は実装の調整で届く。
一方 **1-3（空室が出発点）と §2 の「山が無い」は、いまの設計の必然**である。

現在の設計は「**サンプル部屋1枚・色替えのみ・家具トグル**」で、体験の到達点が
**「空室の壁と床の色が変わる」**ことに固定されている。ここが本質的な天井で、素材を
足しても「もっと綺麗な空室の色違い」にしかならない。ユーザーが模様替えに期待するのは
**「殺風景な部屋が、住みたい部屋になる」**という落差だが、いまの設計はその落差を作れない。

## 4. 2つの道の見込み

### A. 実装を活かして改善する

`ROOM_ENGINE_JS`（面のポリゴン定義＋色替え）と `/try` の枠組みをそのまま使い、
不具合と素材と色を直す。

- **やること**: BEFORE バッジの修正 / `try-furni-1` の配置 / 壁色を振れ幅のある構成に
  入れ替え（中〜濃色を増やす）/ スウォッチの見切れ解消 / ステージを大きく
- **見込み**: 「壊れて見える」状態は確実に脱する。ただし**到達点は「空室の色が変わる」の
  まま**なので、SNS の着地点として「おっ」と思わせるところまでは届かない見込み
- **向く場面**: LP からの補助導線や、アプリの機能説明としてなら十分な水準になる

### B. 設計から作り直す

体験の到達点を「**家具も入って、部屋が仕上がる**」に変える。

- **やること**: 出発点を生活感のある部屋にする／色替えだけでなく**家具が入る**ところまでを
  1タップの流れにする／「3タップで完成」のようにゴールを提示する／`/demo` は色の
  クロスフェードでなく**空室→完成**の落差を見せる構成にする
- **効くのは**: この落差こそが、いま作れていない唯一のものだから。実際、LP の
  before/after が機能しているのは「白い壁＋オーク床 → 水色の壁＋グレー床」という
  **一目で分かる差**があるため
- **コスト**: 家具の権利がクリアな画像が複数点必要（🔴楽天収集品は不可）。面のポリゴン
  定義は部屋写真ごとに実測が要るので、部屋を替えるなら定義もやり直し
- **流用できる**: `ROOM_ENGINE_JS`、面ポリゴンの実測手順、`/demo` のタイムライン機構、
  `/try` のページ構造と計測は**そのまま使える**。作り直すのは素材と演出の設計であって、
  基盤ではない

### 推奨

**B。** ただし A の不具合修正（1-1・1-4・1-6）は B でもそのまま必要になるので、
**先に A の修正を入れてから B の演出設計に進む**のが無駄がない。

なお **B に進む前に、権利がクリアな家具画像を何点用意できるかを先に決めること**。
ここが供給できないと B は成立せず、A で止めるしかなくなる。
