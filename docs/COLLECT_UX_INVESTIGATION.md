## 2. 現在の進捗表示の問題点

1. **最初の7.5秒が完全に無言**（「検索中…」だけ）。何件見つかったかも、あと何秒かも分からない。
2. **分母が「72」**。ユーザーが指定したのは30枚なのに `1/72` と出る。72 は内部の多め取得（over-fetch）の数で、
   **ユーザーには意味が分からない数字**。
3. **残り時間の見通しが無い。**
4. **中止できない。** 35秒待つと決めた人が気を変えても抜けられない。

## 4. いちばん効く一手: 選別フェーズのサムネをその場で出す

`pickBestCandidateThumb()` は**採点のために300pxのサムネイルを既に読み込んでいる**。
いまはその画像を捨てて、後段で改めて原寸を取り直してから初めて表示している。

**採点が終わった商品から順にライブラリへ並べ、原寸が届いたら差し替える**ようにすれば、
**最初の1枚は約9秒（＝選別が数件終わった時点）**で出る。25.5秒 → 約9秒。
以降も1〜2枚ずつ増え続けるので、「動いている」ことが常に見える。

これは**取得の仕方を変えない**（リクエスト数も並列度も同じ）。表示のタイミングだけの変更。

## 6. 「明らかに無駄な直列処理」はあるか（指示025 の3項）

**直列処理は無い。** 検索は1リクエスト、選別は並列6、原寸読込は並列5で、いずれも並列化済み。

ただし事実として、**選別の15.8秒は約216枚の `/imgproxy` 取得が並列6で流れている時間**である。
並列度を上げれば縮むが、これは指示025 の「やらないこと」に当たり、かつ
**楽天CDNとVercel関数へのリクエストが一気に増える**（1枚 = 1関数呼び出し）。
**判断は運営に委ねる。こちらからは実施しない。**

## 9. C7 の修正（指示028 の1項）— 配置した商品はライブラリに残す

### 9.1 選んだ方式と理由

運営から示された2案のうち、**「配置済みの商品を優先的に枚数の中に含める（その分、未配置の下位を1枚落とす）」**を採った。

**理由は「枚数スライダーの数字＝ライブラリに増える枚数」という約束を壊さないため。**
指示027 で「分母はユーザーの指定値」を実測で確認したばかりで（15枚指定 → `15/15 枚` → 15枚追加）、
枠外に残す案だと**31枚になり、完了メッセージ・スライダー・実際の枚数の3つが食い違う**。
実装量はどちらもほぼ同じ（枠外案＝削除ループに条件を1つ、枠内案＝入れ替えループを1つ）で、
**差がつくのは「ユーザーから見て不自然でないか」だけ**だったため、約束が崩れない側を選んだ。

落とされるのは**未配置でいちばん選別スコアが低い1件**で、ユーザーはその商品を一度も選んでいない。
配置済みカードは差し替え対象からも外れているので（指示027 の修正）、置いた商品が別商品に化けることもない。

### 9.2 本番実測 — 入れ替えが実際に走ったことの確認

同じ検索は結果が安定している（`[collect-ranking]` の best/med/worst が毎回一致）ので、
**A) 配置なしで収集した「本来配られる10枚」** と **B) 選別の早い時点で6枚配置した結果** を突き合わせた。

| 確認項目 | 結果 |
|---|---|
| 配置した6枚が最後まで残ったか | **6枚とも残った**（消えたものゼロ） |
| ライブラリの枚数 | **10枚**（スライダーの指定どおり）。完了メッセージも「10 枚をライブラリに追加しました」 |
| **入れ替えが走った証拠** | 配置した6枚のうち **3枚は A（本来の10枚）に入っていなかった** ＝ **配置したから残った**。入れ替わりに未配置の3枚が落ちた |
| 配置した商品の解像度 | **6枚とも 600×600**（原寸。暫定サムネのままではない） |

修正前の同じ手順では `card_still_in_lib: false`（消える）だった。

### 9.3 修正後の通常フローの実測（本番・ソファ・30枚・3回）

## 10. C6 の再現手順（指示028 の2項）— 運営が見て判断するために

### 10.1 まず前提: **スクロールしないと見えない**

実測した DOM の位置関係（1424×805 のウィンドウ）:

| | |
|---|---|
| 右パネルの表示域（`div.scroll`） | 画面の **y = 92 〜 779**（高さ 687px） |
| ライブラリ（`#furniLib`）の先頭 | **y = 1281** |

**つまり既定の位置のままだと、ライブラリは表示域の遥か下にあり、並び替えは1枚も目に入らない。**
収集ボタンのあたりを見ているだけでは何も起きていないように見える。
**確認するには、収集ボタンを押したあと右パネルを下までスクロールし、ライブラリを画面に入れたまま待つこと。**

### 10.2 いつ起きるか

**選別が終わる瞬間、1回だけ。** 状態表示が
「画像を集めています… **N/N 枚**」→「**画像を鮮明にしています…**」に変わる、まさにその瞬間。
ソファ30枚なら**開始から約13秒**。見逃したらもう起きない（以降カードは 0.0px しか動かない）。

### 10.3 枚数ごとの大きさ（本番実測・ライブラリを画面に入れた状態）

表示域には**一度に21枚**（7行×3列）が入る。

| 指定枚数 | 実際の枚数 | 動いたカード | 最大移動 | 移動量の中央値 | **見えている範囲での中央値** |
|---|---|---|---|---|---|
| **10枚** | 10 | 9 / 10 | 322 px | 201 px | **201 px**（1〜2行ぶん） |
| **30枚**（既定） | 30 | 30 / 30 | 845 px | 322 px | **322 px**（3行ぶん） |
| **80枚** | 71 | 65 / 71 | **2172 px** | 832 px | **1241 px**（表示域 687px の約1.8個ぶん） |

**いちばん顕著に出るのは「楽天全体・ソファ・80枚」。**
見えている21枚の位置が中央値1241px動く＝**画面に映っているカードがまるごと入れ替わって見える。**
既定の30枚では3行ぶん（322px）ずれる程度。10枚ならほとんど気にならない。

### 10.4 運営向けの手順（そのままなぞれる）

1. roomstudio.jp を開き、部屋の画像を1枚読み込む
2. 右パネルの「家具を収集」で **ソファ / 楽天全体 / 枚数を80** にする
3. 「収集する」を押す
4. **すぐに右パネルを下までスクロールし、ライブラリの領域を画面に入れたまま待つ**
5. 進捗が「画像を集めています… 71/80 枚」から「**画像を鮮明にしています…**」に変わる瞬間（約13秒）を見る
6. 30枚・10枚でも同じ手順で見比べる（既定は30枚なので、実際のユーザーが見るのは30枚の挙動）

**判断してほしいこと**: これは不具合ではなく「配る順番の確定」で、従来コードにも同じ処理があった
（従来は6枚ごとに繰り返し・1回あたり172px＝回数が多く1回は小さい。いまは1回だけ・1回は大きい）。
消すには「配る順番を選別の途中で確定させる」＝並び順の意味そのものを変える必要がある。

## 11. スマホ実機で収集を試すときに見る点（指示028 の3項・A1）

SAM 側の手順は `docs/PERF_INVESTIGATION.md` §8「運営向けの実機確認手順」。ここは**収集**のぶん。
手順は「部屋の写真を1枚読み込む → 家具を収集（ソファ・30枚）→ 収集する を押す」だけ。

| # | 見るところ | 期待（デスクトップ実測） | 気にしてほしい理由 |
|---|---|---|---|
| **1** | **最初の1枚が出るまで** | **7秒台**（デスクトップは 7.1〜7.6秒） | 最重要指標。回線が遅い実機でどこまで伸びるか。**10秒を大きく超えるなら報告してほしい** |
| **2** | **検索中の経過秒が動いているか** | 「楽天から商品を探しています… **3.4秒**（この間もほかの操作ができます）」が0.1秒ごとに更新 | 止まって見えたら、その端末では進捗が出ていない |
| **3** | **その文言が何行になるか** | デスクトップは2行。**収集中だけ 4.6em の高さを予約**している | **狭い画面で5行以上に折り返すと予約高さを超え、文言が変わるたびにライブラリ全体が上下に動く。**スマホで最も出やすい崩れ方なので、ここは特に見てほしい |
| **4** | **進捗の分母** | 「画像を集めています… 12/**30** 枚（候補 34/71 件を確認中）」＝**スライダーで指定した数** | 枚数を30以外にして確かめると分かりやすい |
| **5** | **中止ボタン** | 収集ボタン自体が「**中止する**」に変わる。押すと即座に止まり、集まったぶんは残る | **ボタンが増えないので位置は動かない。**逆に、**開始直後にもう一度タップすると中止になる**ので、誤タップしやすくないかを見てほしい |
| **6** | **収集中に他の操作ができるか** | スクロールも他のボタンも効く | デスクトップの実測ではクリック受理率 78〜86%。実機で「触れない」感じがあれば報告 |
| **7** | **並び替えの瞬間**（→ §10） | 選別が終わる瞬間に一度だけ並びが変わる | **スマホは画面が狭いぶん、デスクトップより目立つ可能性が高い。**判断材料として見ておきたい |
| **8** | **カードを置いてから収集完了まで** | 置いた商品がライブラリに残り、部屋の家具も原寸のまま | §9 で直したところ。実機でも同じか |

**画像が1枚も出ない時間は 0 → 7秒台（検索フェーズ）だけ**で、その間も経過秒が動いている。
それ以外に無言の区間があれば、それはデスクトップでは出ていない実機固有の症状。
