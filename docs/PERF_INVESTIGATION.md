# 体感の遅さはどこから来ているか — コンソール警告の調査（指示020）

2026-07-30。**調査のみ。コードは1行も変えていない。** 実装方針は運営が判断する。

---

## 0. 結論

**「クリックが3秒固まる」「28.5MBの保存」「getImageData の警告」は、ばらばらの問題ではなく
1つの原因の別々の症状。原因は次の1点に集約される。**

> **作品の中身（部屋・家具・収集した画像）を、すべて base64 の PNG 文字列として1つの巨大な
> オブジェクトに詰め、それをユーザー操作と同じスレッドで、保存のたびに作り直している。**

そのうえで、**性質の違う問題がもう1つある**:

> **SAM（AIの範囲選択）の推論がメインスレッドで走っており、1回 6.5秒 UI が完全に止まる。**
> WebAssembly の警告2つはこれが原因。**実はこちらのほうが遅い。**

実測した「UIが固まっていた時間」（1msタイマーの途切れで計測。この値のあいだスクロールも
クリックも一切効かない）:

| 操作 | 固まる時間 | 内訳 |
|---|---|---|
| **SAM の画像解析**（面ツールで最初にクリックした時 / 部屋を替えた時） | **6,458 ms** | 推論そのもの（1回の連続ブロック） |
| **MY作品に保存**（収集直後＝PNG未キャッシュ） | **1,153 ms** | PNGエンコード 1,693ms のうち |
| 自動保存（タブ切替・編集2.5秒後） | 143 ms | キャッシュ後。未キャッシュだと約1.7秒 |
| 色を変える（色チップ） | 実測 35〜56 ms | **犯人ではない** |
| 元に戻す / やり直す | 340 ms | |
| レイヤー削除 | 270 ms | |
| モード切替（表面⇄家具） | 0.2 ms | |
| 作品をファイルに保存（`[save] 28.5MB` が出る操作） | 302 ms | 26.4MB を stringify + Blob |

**運営が見た `'click' handler took 3069ms` は、ほぼ確実に「保存」系のクリック**である。
この環境（後述）で「MY作品に保存」を収集直後に押すと **2,272 ms**。運営の実機は
ヘッドレス+ソフトウェア描画のこの環境より遅いのが普通なので、3,069ms は無理なく届く。
1,740ms / 1,647ms は2回目以降の保存、または「元に戻す」の連打で説明がつく。

**逆に、当初いちばん疑わしかった「色替え」は35msで、原因ではなかった。**
（`pushHistory` の全画面 `getImageData` も 1.5ms で、これも原因ではない。）

| | |

  （アプリが「準備完了（WebGPU）」と出すか「準備完了（CPU）」と出すかで分かる）。

## 2. 一本の原因: 「巨大な base64 の塊を、毎回その場で作り直す」

### 2-1. 保存されるデータの正体

`buildProjectObject()`（`room-studio.html`）が作るオブジェクトの中身は、ほぼ全部が
**PNG を base64 にした文字列**である。base64 は元のバイト列より **33% 大きい**。

実測した内訳（部屋 1100×825・配置20点の場合）:

| 中身 | サイズ | 備考 |
|---|---|---|
| `room`（編集後の部屋PNG） | 2.4 MB | 保存のたびに**再エンコード**（キャッシュ対象外） |
| `roomOriginal`（編集前の部屋PNG） | 2.4 MB | 元画像が変わらない限りキャッシュされる |
| 配置済み家具の画像（`src` + `aiCut`） | 約 19 MB | 1点あたり 0.7MB×最大2枚 |
| 表面マスク（base64） | 1.2 MB | 面の数だけ増える |
| **小計＝ファイル保存の JSON** | **26.4 MB** | **運営が見た 28.5 MB とほぼ一致** |
| ＋ 収集ライブラリ `furniLib` | **+0.7 MB × 枚数** | 30枚収集で +21MB、100枚で +70MB |
| **＝自動保存 / MY作品に保存の JSON** | **118 MB**（ライブラリ130枚時） | |

> **`[save] current JSON size: 28.5 MB` の 28.5MB は「配置済み家具ぶん」**。この経路
> （`saveCurrentToFile`）は `forFile:true` で**収集ライブラリを除外している**。つまり運営の
> 作品には**配置済み家具が20点前後ある**と推定できる（実測26.4MBが配置20点）。
> **自動保存とMY作品保存はライブラリも含むので、実際にはこの数倍が書かれている。**

### 2-2. なぜクリックが固まるのか

「MY作品に保存」を押したときに**同期で**走る処理（実測・収集直後＝PNGキャッシュが冷たい状態）:

| 段階 | 時間 |
|---|---|
| `render()` | 12 ms |
| `stageThumb(320)`（サムネ） | 2 ms |
| `stage.toDataURL('image/png')`（合成画像のPNG） | 31 ms |
| **`buildProjectObject()`** | **1,693 ms** ← ここが全部 |
| （同期ここまで） | **1,737 ms** |
| `idbPut()`（IndexedDBへ書き込み） | 535 ms |
| **合計** | **2,272 ms**（うち UI 完全停止 1,153 ms） |

`buildProjectObject` の 1,693ms の正体は **PNG エンコードの山**である。
1枚あたり実測: 600×600 の家具画像 = **9.4 ms**、1100×825 の部屋 = **34 ms**。
ライブラリ100枚＋配置20点（＋AI切り抜き10点）＝ 130回前後のエンコードで約1.7秒。

**2回目以降は 142ms に落ちる。** `_pngCache`（`WeakMap`）が効くため。
つまり**「収集した直後の最初の保存」だけが極端に遅い**。運営が見た 3069ms と 1740/1647ms の
差も、これで説明がつく。

### 2-3. なぜタブを切り替えるだけで重いのか（指示020-2 の答え）

```
room-studio.html:4284
on(document,'visibilitychange',()=>{ if(document.visibilityState==='hidden'){ try{ doAutosave(); }catch(e){} } });
```

**タブを隠すたびに、条件なしで作品まるごとを保存している。**
`doAutosave()` は `buildProjectObject({forCloud:false})`（＝**収集ライブラリ込み**）を作って
IndexedDB に書く。実測 **317ms（UI停止 143ms）**、PNGキャッシュが冷たければ約1.7秒。
**5回のタブ切り替えで5回とも走る。変更が無くても走る。**

さらに `render()` が**毎回** `scheduleAutosave()` を呼んでいる（2.5秒デバウンス）ので、
**編集して2.5秒手を止めるたびに同じ処理が走る**。これは `'click'` ではなく
`'setTimeout'` の Violation として出る。

### 2-4. 保存の失敗はどうなるか（指示020-3 の答え）

| 経路 | 失敗時 |
|---|---|
| MY作品に保存 | `QuotaExceededError` を捕まえて **トーストで通知**（「保存容量が足りません」）✅ |
| **自動保存** | `catch(e){ console.warn('autosave failed', e); }` ← **黙って失敗する** ❌ |
| ユーザー素材の保存 | `console.warn` のみ ❌ |

**自動保存が容量で失敗しても、ユーザーには何も表示されない。**
「編集が保存されていると思っていたのに、リロードしたら消えていた」が起きうる。

### 2-5. ストレージ上限との距離

- この環境（デスクトップChrome）の実測: **quota 10.2 GB / 使用 30.6 MB** → 余裕あり。
- **モバイル Safari は別物で、ここでは測れていない。** 確かなのは次の2点:
  - 1作品 100MB超・自動保存 118MB という**桁が、モバイルの現実的な割当に対して大きすぎる**。
  - Safari は「7日間アクセスがないサイトのスクリプト書き込みストレージを消す」挙動があるため、
    **IndexedDB を長期の保管場所として当てにできない**。
- **やるべき確認**: 実機（iPhone Safari）で `navigator.storage.estimate()` を見る。
  これは実装ではなく計測なので、判断の前に取れる。

### 2-6. 増え続ける構造か（指示020-3 の答え）

**増え続ける。** 収集するたびに `furniLib` に 0.7MB × 枚数（既定30枚＝約21MB）が積まれ、
**それが自動保存とMY作品保存の両方に毎回丸ごと入る**。3カテゴリ収集すれば60MB超。
頭打ちにする仕組みは無い（ライブラリを手で消す以外に減らない）。

> ⚠️ **規約の観点でも整合していない。** `docs/COLLECT_QUALITY_RESUME.md` 以来
> 「楽天画像は都度取得・非保存」を原則にしてきたが、**収集画像は現状 IndexedDB に
> 恒久保存されている**（自動保存とMY作品の中に base64 で）。ここは性能とは別に判断が要る。

### 2-7. メモリ（今回発見した副産物）

`captureState()` は**部屋の全画素（ImageData）とマスク全体をコピー**する。
1手あたり **4.3 MB**、`HISTORY_MAX=20`、undo と redo で最大40手 → **最大 172 MB**。
モバイルではタブ落ちの原因になりうる。1手の取得自体は 2.4ms と速いので**体感は悪くないが、
メモリだけが静かに積み上がる**。

## 3. もう一本の原因: AI がメインスレッドで動いている（指示020-5 の答え）

### 3-1. 実測

| | 時間 |
|---|---|
| モデル読み込み（初回・ネットワーク込み） | 9,051 ms |
| **画像の解析（`ensureSamEmbeddings`）** | **6,576 ms（うち UI 完全停止 6,458 ms）** |
| 2回目（部屋を替えた時など） | 7,851 ms |
| クリック1回のデコード | 274 ms |

**6.4秒間、1回の連続ブロックとして UI が止まる。** これはアプリ全体で最悪の停止時間で、
保存の1.1秒より圧倒的に長い。**運営が「クリックが3秒」で気づいた問題より、こちらが重い。**

### 3-2. 警告の意味

```
WebAssembly multi-threading is not supported. Falling back to single-threading
env.wasm.numThreads is set to 12, but this will not work unless you enable crossOriginIsolated mode
```

onnxruntime-web は 12スレッド（＝CPUコア数）で回そうとしたが、**`SharedArrayBuffer` が
使えないので1スレッドに落ちた**、という意味。実測でも `crossOriginIsolated: false` /
`SharedArrayBuffer: undefined` を確認した。

### 3-3. crossOriginIsolated を有効にするには何が要るか

ドキュメント（HTML）のレスポンスに次の2つを付ける:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp   （または credentialless）
```

**Vercel では設定できる。** 現状 `vercel.json` は無く、ページは FastAPI（`api/index.py` /
`api/_site.py`）が返しているので、**レスポンスヘッダを1か所足すだけで足りる**
（`/try`・`/demo`・LP も同じ経路）。

### 3-4. 副作用の評価（最優先で見た）— **実測した**

COEP を有効にすると、**CORS でない（no-cors）外部リソースは `Cross-Origin-Resource-Policy`
が無いと全部ブロックされる**。アプリが読む外部リソースを全部叩いて確認した:

| リソース | CORP ヘッダ | 判定 |
|---|---|---|
| `fonts.googleapis.com`（CSS） | `cross-origin` | ✅ 通る |
| `fonts.gstatic.com`（フォント本体） | `cross-origin` | ✅ 通る |
| **`www.googletagmanager.com/gtag/js`（GA4）** | `cross-origin` | ✅ 通る |
| **`www.google-analytics.com/g/collect`（GA4の送信先）** | `cross-origin` | ✅ 通る |
| `cdn.jsdelivr.net` / `unpkg.com`（transformers.js・背景除去） | `cross-origin` | ✅ 通る |
| HuggingFace のモデル本体（`cdn-lfs`） | CORP は無いが `ACAO: *` | ✅ 通る（CORSフェッチなので CORP 不要） |
| **楽天の商品画像** | — | ✅ **同一オリジンの `/imgproxy` 経由なので影響なし** |

**＝ 収益導線（GA4・アフィリエイトリンク）は壊れない見込み。** 楽天画像もサーバ経由なので
無関係。COOP: same-origin は `window.opener` を切るが、アフィリエイトは URL 遷移なので影響しない。

**ただし「見込み」であって、有効化して実機で確認するまで断定はできない。**
ヘッダを足す作業自体は小さいが、**判断は「まず staging で1本デプロイして確認」にすべき**。

### 3-5. しかし、スレッドを有効にしても本命は解決しない

**マルチスレッド化で速くなるのは推論そのもの（経験的に2〜3倍）だが、
「メインスレッドで走っている」ことは変わらない。** 6.5秒が2〜3秒になっても、
その2〜3秒は依然として**UIが完全に固まる**。

**本命は Worker への退避**（推論を別スレッドで走らせる）。これなら
「解析中…」の表示を出したまま、ユーザーは他の操作ができる。
次点で**入力解像度を下げる**（SlimSAM は 1024×1024 入力。部屋を縮小して渡せば線形に近く効く）。

## 4. getImageData / willReadFrequently（指示020-4 の答え）

`getContext('2d')` は全46か所、うち `willReadFrequently:true` 付きは8か所。
**警告を出しているのは、繰り返し読み戻すのにフラグが無い次の2か所**と考えられる:

| 場所 | 何をしているか | 頻度 |
|---|---|---|
| `room-studio.html:1046` `sctx = stage.getContext('2d')` → `sampleStageColor`（2482行） | スポイトのルーペが**マウスを動かすたび**に合成画像から5×5画素を読む | mousemove ごと |
| `litRoomBase()`（1057〜1064行） | 明るさスライダーを動かすたび**部屋の全画素**を読み書き | スライダー操作ごと |

**改善見込みは小さい。** この環境での実測:

| | 1回あたり |
|---|---|
| `stage`（フラグ無し）から 5×5 読み出し ×200回 | **0.01 ms** |
| フラグ付き canvas から同じ読み出し | **0.00 ms** |
| 明るさ適用（全画素 LUT・1100×825） | 11 ms（2回目以降はキャッシュで 0ms） |

**ただし §1 のとおり、この環境は `--disable-gpu` なので読み戻しのペナルティが出ない。**
実機（GPU合成）では `stage` からの読み戻しは桁で遅くなりうる。
**フラグを足すコストはほぼゼロ・副作用も実質無い**ので、
「効果は測れていないが、入れない理由も無い」という位置づけ。

**3秒の犯人ではない。** ここを直しても体感は変わらない。

## 5. 改善案 — 効果 × コスト × リスク

**効果**＝体感（UIが固まる時間）への効き。**コスト**＝実装量。**リスク**＝壊れうる範囲。

| # | 案 | 効果 | コスト | リスク | 備考 |
|---|---|---|---|---|---|
| **A** | **収集ライブラリの画像を自動保存の対象から外す**（URLだけ持ち、必要時に再取得） | **大** 自動保存 118MB→約5MB・保存クリックの大半が消える | **小** | 小 | セッション復元後にライブラリの画像が消える（再収集が要る）。**楽天「都度取得・非保存」の原則にはむしろ合う** |
| **B** | **保存形式を base64 PNG → Blob（または WebP）に** | **大** 容量 1/5〜1/10、エンコードも軽い | 中 | 中 | IndexedDB は Blob をそのまま保存できる。既存データの読み込み互換が要る。WebP は透過も保てる |
| **C** | **タブ切替の自動保存を「前回から変わっていたら」に限定** | 中 | **小** | 小 | 今は無条件。5回のタブ切替で5回とも走っている |
| **D** | **SAM の推論を Worker に出す** | **大** 6.5秒のUI停止が消える（待ち時間そのものは残る） | 中〜大 | 中 | transformers.js は Worker 前提の使い方ができる。**体感への効果は今回いちばん大きい** |
| **E** | **COOP/COEP を付けて WASM マルチスレッドを有効化** | 中 推論 2〜3倍（6.5秒→2〜3秒）だが**固まることは変わらない** | **小** | 小〜中 | 外部リソースは全部 CORP 付きで通る見込み（§3-4 で実測）。**D と組み合わせて初めて活きる** |
| **F** | **PNG エンコードを `toBlob` / OffscreenCanvas + Worker に** | 中〜大 保存クリックの固まりが消える | 中 | 小 | A・B をやれば残りは小さいので、A・B の後に効果を測ってから |
| **G** | **自動保存の失敗をユーザーに伝える** | 小（体感は変わらない） | **小** | なし | 現状は黙って失敗する。**信頼性の問題としては優先度が高い** |
| **H** | **`willReadFrequently` を `stage` と `litRoomBase` に付ける** | **小**（実機では未知） | **極小** | なし | 警告は消える。3秒の原因ではない |
| **I** | **`HISTORY_MAX` を下げる / 差分履歴にする** | 小（体感）・中（メモリ） | 中 | 中 | 最大172MB。モバイルのタブ落ち対策 |
| **J** | **SAM の入力解像度を下げる** | 中 | 小 | 中（選択精度が落ちる） | D で固まらなくなれば優先度は下がる |

### 私の推奨順

1. **A → C → G**（小さい実装で、いちばん大きい体感改善と、黙って失敗する問題の解消）
2. **D**（6.5秒の固まりを消す。体感としてはこれが最大）
3. **B**（容量の桁を下げる。モバイルの保存失敗リスクにも効く）
4. **E**（D の後に。単独では「固まる時間が短くなるだけ」）
5. **H**（ついでに。警告は消える）

**測り直しの基準**: 改善したかどうかは、**1msタイマーの途切れ（UIが固まった時間）**で測ること。
「JSONが何MB減った」ではユーザーの体感を保証できない（指示019 で決めた「見た目・体感で判断する」
と同じ考え方）。計測方法は §1 のとおり、再現できる形で残してある。

## 6. 今回わかった、指示に無かったこと

- **色替えは遅くない**（35ms）。最初の見立ては外れだった。
- **`[save] 28.5 MB` の経路（ファイル保存）は 302ms しかかからない。** 3秒の犯人は
  **MY作品に保存**のほう。ログの隣に出ていた 28.5MB は「作品がそれだけ重い」ことの証拠であって、
  遅さの直接の原因ではない。
- **アプリ最大の停止は SAM の 6.5秒**で、コンソールの警告からは「単なる注意書き」に見えていた。
- **収集画像が IndexedDB に恒久保存されている**（性能ではなく規約側の論点）。
